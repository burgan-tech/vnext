# Live evidence — task invocation routing (issue #1007)

Measured **2026-09-19** against the local stack (`etc/docker/run-docker.sh up core`), hosts built
from `1007-run-httptask-and-daprservicetask-from-orchestration-instead-of-execution` @ `8d6e5a03`,
traffic generated by the `task-invocation-lab` scenario in vnext-example.

Two questions are answered here, in this order, because the second is worthless without the first:

1. **Did the trace tree break?** Moving five task types in-process removes the Execution service's
   whole span subtree from every one of their traces. If the replacement path emitted nothing, the
   work would simply vanish from the trace and every duration below would be measuring a hole.
2. **What does the hop actually cost?** Issue #1007 asserts the extra hop buys nothing. It had never
   been measured.

**Read in Elasticsearch, not OpenObserve** — same reason as
[2026-09-13-route-trace-coverage](../2026-09-13-route-trace-coverage/README.md): Elastic resolves
nesting strictly through `parent.id`, so it is the renderer that can disprove a parentage claim.
Index pattern `traces-apm*`. The `elasticsearch` and `openobserve` MCP servers both failed to
connect in this session; everything below was read over plain HTTP against `localhost:9200`.

## Method

Both modes were measured on the **same** hosts, the same components and the same MockLab, with
**only** `Workflow:TaskInvocation:Modes:*` differing. Each mode was restarted, warmed with three
iterations per case, then measured over 20. Windows:

| Mode | Window (UTC) |
|---|---|
| Local (shipped default) | `15:22:12` .. `15:22:29` |
| Remote (every type forced back) | `15:23:20` .. `15:23:38` |

## 1. Trace integrity — no span family is missing in either mode

Per-trace check over every transition trace in the window: does it still carry
`Instance.Activation`, `Task.Execute.*`, `Task.Invoke`, `Task.PrepareInput`, `Task.ProcessOutput`,
`Transition.Settle` and `Uow.Commit`, and is every span's `parent.id` present in its own trace?

| | Local | Remote |
|---|---:|---:|
| Transition traces | 172 | 146 |
| Missing a required span family | **0** | **0** |
| `Task.Invoke` spans carrying `vnext.task.invocation.mode` | 172 / 172 | 146 / 146 |
| Transition outcome `success` | 172 / 172 | 146 / 146 |
| Orphan spans other than the pubsub pair below | **0** | **0** |

The only structural orphans are `pubsub/development.aether.outbox.wakeup.v1` and
`pubsub/development.instance.completed.cleanup.v1`, **exactly one of each per transition in both
modes**. These are Dapr sidecar producer spans whose wire parent is filtered out — the pre-existing
condition described in `docs/runtime/trace-lanes.md`; their count is identical in both modes, so
they are not a product of this change.

> **Measurement trap, recorded because it produced a false positive first.** Paginating the window
> with `search_after` on `@timestamp` alone silently **skips** documents — the field is not unique,
> and ~0.1 % of spans were dropped, orphaning their children and manufacturing "missing" span
> families. Both effects disappeared under a PIT read with a `_shard_doc` tiebreaker. A second,
> smaller artefact is real and unavoidable: a trace straddling the window edge loses its root, so a
> handful of edge spans always look orphaned. Widen the window and they move rather than persist.

### The two shapes, side by side

Local — the Execution subtree is gone and the outbound call hangs directly off `Task.Invoke`:

```
Task.Execute.til-http-ok                       vnext_task_type=Http
  Task.Invoke                    [5.9 ms]      vnext_task_invocation_mode=Local
    Invoke.Prepare               [0.0 ms]      vnext_task_type=http
    POST →localhost:3001         [5.0 ms]
```

Remote — identical inner work, wrapped in the service hop:

```
Task.Execute.til-http-ok                       vnext_task_type=Http
  Task.Invoke                    [8.3 ms]      vnext_task_invocation_mode=Remote
    Dapr invoke vnext-execution-app  [6.3 ms]
      CallLocal/vnext-execution-app/api/v1/execution/invoke/http/til-http-ok
        POST api/v{version}/execution/invoke/{type}/{key}   <vnext-execution-app>
          Execution.HandleInvoke   [6.1 ms]
            Invoke.http/til-http-ok
              Invoke.Prepare       [0.0 ms]
              POST →localhost:3001 [5.9 ms]
```

Two span names exist only on the Remote path (`Execution.HandleInvoke` and `Invoke.{type}/{key}`,
both emitted inside the Execution host). Nothing is lost by their absence: `Task.Invoke` covers the
same interval on the Orchestration side, and `Invoke.Prepare` plus the outbound client span survive
because the shared invocation cores moved with the code and
`BBT.Workflow.Execution.Invokers` is registered in the Orchestration host's `AdditionalSources`.

## 2. What the hop costs

`Task.Invoke` p50, same window, same components:

| Wire type | Local | Remote | Δ | Remote inner work (`Execution.HandleInvoke`) |
|---|---:|---:|---:|---:|
| `http` | 5.87 ms | 8.29 ms | **+2.42 ms** | 6.14 ms |
| `soap` | 6.46 ms | 8.34 ms | **+1.88 ms** | 6.46 ms |
| `statestore` | 0.69 ms | 2.24 ms | **+1.55 ms** | 0.71 ms |
| `cacheaside` | 0.70 ms | 2.40 ms | **+1.70 ms** | 0.66 ms |

Two independent derivations agree. Subtracting *across* modes (Local vs Remote `Task.Invoke`) gives
1.55–2.42 ms; subtracting *within* the Remote mode (`Task.Invoke` minus `Execution.HandleInvoke`,
i.e. transport only) gives 1.53–2.15 ms. And for every type **Local `Task.Invoke` ≈ Remote
`Execution.HandleInvoke`** (5.87/6.14, 6.46/6.46, 0.69/0.71, 0.70/0.66): the invocation work itself
is unchanged, only its transport differs.

**The honest end-to-end conclusion.** At one task per transition the saving is ~1.5–2.4 ms against a
30–50 ms transition, which is inside run-to-run variance — the client-side p50s move in both
directions across cases (`http-ok` −13.2 ms, `statestore-set` +1.6 ms in Local's favour and against
it respectively). The hop's cost is real, consistent and cheap to remove; it is **not** a
transition-level speedup that a single measurement can demonstrate. It multiplies with task count
per transition, which is where it will be visible.

## 3. The cache paths

### `cacheaside` task (p50, Local window)

| | Local | Remote |
|---|---:|---:|
| `Task.Invoke` on a **hit** | 0.69 ms | 2.17 ms |
| `Task.Invoke` on a **miss** | 7.96 ms | 9.47 ms |
| `CacheAside.Read` | 0.61 ms | 0.55 ms |
| `CacheAside.Write` (miss only) | 0.59 ms | 0.65 ms |
| Whole transition | 31.2 / 37.4 ms (hit/miss) | 32.8 / 41.4 ms |

The cache itself is worth ~7.3 ms per hit at the seam; routing it locally is worth a further
~1.5 ms on both branches.

### Function response cache (`IStateStoreCacheGateway`)

This is the path with no prior coverage anywhere: **no component in vnext-example configured
`function.cache`**, so the gateway and the `Cache.Get`/`Cache.Set` spans it emits under component
type `function-response` had never been reached end to end. The lab now carries `til-cached-echo`
for exactly this (see the scenario README in vnext-example).

| Span | Local | Remote | Δ |
|---|---:|---:|---:|
| `Cache.Get` (hit) | 0.684 ms | 2.188 ms | +1.50 ms |
| `Cache.Get` (miss) | 0.752 ms | 2.287 ms | +1.54 ms |
| `Cache.Set` | 0.710 ms | 1.796 ms | +1.09 ms |

End to end on the function endpoint: a hit answers in **1.55 ms** against a miss's **9.69 ms**
(Local), and **3.24 ms** against **12.93 ms** (Remote). The hop cost here matches the wire types
exactly, which is the point — the gateway is on the same seam and behaves like one of them.

## Reproducing

```bash
cd etc/docker && ./run-docker.sh up core --offset 0
cd ../../../vnext-example && wf domain use core && wf sync
dotnet test tests/Core.IntegrationTests --filter "FullyQualifiedName~TaskInvocationLab"
```

To measure the Remote side, export the five `Workflow__TaskInvocation__Modes__*=Remote` keys plus
`Workflow__TaskInvocation__DefaultMode=Remote` **before** restarting the hosts (the options bind
once at startup — see [task-invocation-routing.md](../../task-invocation-routing.md)), then repeat.
