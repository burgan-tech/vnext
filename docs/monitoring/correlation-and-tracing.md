# End-to-End Correlation and Distributed Tracing

How a client request (instance start / transition) stays observable as **one trace tree** across
Orchestration → background jobs → Execution → remote tasks, and how logs stay joinable to the
originating request via **X-Request-Id** — including through the APISIX gateway.

## The two correlation carriers

| Carrier | Purpose | Where it lives |
|---|---|---|
| W3C `traceparent` / `tracestate` | One trace tree in APM (Elastic, OpenObserve, Jaeger) | HTTP headers (auto-injected by .NET HttpClient), job payloads (`ITraceableJobPayload`), event contracts (`ITraceableDistributedEvent`), `TaskTraceContext` |
| `X-Request-Id` | Log correlation back to the client request | HTTP header, read/generated by Aether's `AetherCorrelationIdMiddleware`; forwarded on every internal hop; attached to log records as `RequestHeader.x_request_id` (enricher) and `vnext.request.id` (scopes) |

The instance id (`vnext.instance.id`) is the third, business-level axis: every span and log scope
on both the write path (`TransitionExecutor.BuildLogScope`) and the read/function path
(`InstanceQueryAppService.BeginInstanceScope`) carries it.

## Gateway (APISIX) requirements

vNext expects the edge gateway to establish both carriers:

1. **`request-id` plugin** — pass the client's `X-Request-Id` through when present, generate one
   otherwise. vNext echoes it on every response (Aether correlation middleware), so the client can
   log it even when the gateway generated it.
2. **`opentelemetry` plugin** — makes the gateway span the trace root and injects `traceparent`
   downstream. vNext's ASP.NET Core instrumentation honors the incoming `traceparent`, so the
   whole server-side tree hangs under the gateway span.

Response headers the platform returns on start/transition calls:

| Header | Content |
|---|---|
| `X-Request-Id` | The request id (echoed or generated) |
| `X-Trace-Id` / `X-Span-Id` / `traceparent` | W3C trace identifiers of the server span |
| `X-Workflow` | `{domain},{workflow},{version},{instanceId}` — the instance id is available to the client immediately after start |

**Client recipe:** capture `X-Request-Id` and `X-Workflow` from the start response. Log searches by
that request id return the full server-side path of the start (including the
`InstanceStarted` record, EventId 20008, which joins request id → instance id); all subsequent
function calls (state long-poll, view, schema, data) are then trackable by `vnext.instance.id`,
and each poll's own `X-Request-Id` is echoed back for per-call debugging.

## Trace-continuation semantics for background jobs

Async processing (`sync=false`) runs transitions as Dapr Jobs. The Dapr scheduler callback is a
fresh HTTP request, so job handlers restore the trace explicitly
(`BackgroundJobActivityHelper`):

| Job | Policy | Result in APM |
|---|---|---|
| `flow.transition` (async transitions, auto-chain steps) | **Continues the original trace** — payload `TraceParent` is the span's parent; the Dapr callback span is attached as an `ActivityLink` (`vnext.dapr.callback=true`) | Client request → job → pipeline → Execution → remote task: one tree |
| `state.notify` | Continues the original trace (fires ~5 ms after enqueue) | Same tree |
| `flow.transition.schedule` (timers), workflow timeout, long-poll ack timeout | **New trace + `ActivityLink`** to the arming trace | Separate tree, linked — deliberate: these fire minutes-to-days later and must not resurrect (possibly expired) traces |

The same continue-with-link semantics apply on the outbox → pub/sub → Inbox path: lifecycle events
implement `ITraceableDistributedEvent`, stamped centrally by `HookedDistributedEventBus` at publish
time, and restored by `EventTraceScope` in the Inbox handlers.

Sampling note: because immediate jobs are real children of the client request's trace, they
inherit its sampling decision — an unsampled request produces an unsampled background chain. This
is the correct default for consistent traces.

## Reserved headers in task bindings

Task binding header definitions (`binding.Headers` on http/soap/daprservice/trigger tasks) must
not carry `traceparent`, `tracestate`, `baggage`, or `x-request-id` — the invokers skip these keys
(`InvokerHelpers.IsReservedTraceHeader`). The live values are injected automatically:
`traceparent`/`tracestate` by .NET's HttpClient instrumentation, `X-Request-Id` by the invoker
infrastructure. A stale traceparent copied into a task definition would detach the downstream
service from the live trace; that's why the guard exists. For Dapr binding/pub-sub tasks (no
HttpClient in the path) the invokers stamp the live context into the operation metadata
(`traceparent` / `cloudevent.traceparent`).

## Telemetry configuration

- **OTLP endpoint**: `Telemetry:Otlp:Endpoint` is intentionally NOT set in `appsettings.json` —
  Aether treats config as stronger than environment, so a hardcoded value would silently override
  `OTEL_EXPORTER_OTLP_ENDPOINT`. Containers set `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318`
  (http/protobuf); bare-metal falls back to `http://localhost:4318`. Elastic APM ingestion is plain
  OTLP — pointing the collector's exporter at Elastic is an ops-side change only.
- **Workers**: Inbox/Outbox have `TracingEnabled: true` so the subflow completion / continuation
  path is visible in APM (they were previously log-only).
- **Detail level**: `Telemetry:Tracing:DetailLevel` — `"Business"` (default) keeps production
  traces focused on service boundaries and business spans; `"Verbose"` additionally emits
  task-phase spans (`BBT.Workflow.Tasks`), cache spans (`BBT.Workflow.Cache`), EF Core and Dapr
  state-store spans. Read once at startup — changing it requires a restart.

## What to check when a trace looks broken

1. Spans missing entirely → is the OTLP endpoint reachable? Remember: config overrides env for
   the endpoint — `Telemetry:Otlp:Endpoint` must stay unset in appsettings.
2. Job spans in their own trace → expected for timer/timeout/ack jobs (follow the link); a
   `flow.transition` job in its own trace means the payload arrived without `TraceParent`
   (check the producer).
3. Execution span in a different trace with `vnext.trace.mismatch=true` → the transport-level
   traceparent disagreed with the body's `TaskTraceContext` — trust the transport, investigate
   the caller.
4. Logs missing the request id on the async path → the originating request never carried/received
   an `X-Request-Id` (gateway plugin disabled?); the middleware generates one per request, so
   at minimum the start request's own logs always have one.
